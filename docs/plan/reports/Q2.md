## 2. Decisions

- **Levels of the old lines.** A line that started with `*ERROR:`, `ERROR:` or `*` in a validation is an error; `!` a warning;
  an unmarked line is information. The levels did not change except where the old logger lied: a validation's errors were logged as
  warnings, now they are errors (Output Log counts go up by that). The lines that explain a failure but were plain (a missing wave,
  a light control) stay information; the "check failed" lines that followed them were and are errors.
- `Finding` has no code and no place (a `Problem` has both); a producer's caller attaches the object (`level.problems` does by
  the first quoted name). `Severity::Required` has no finding: `Log::finding` logs it as information.
- **Dialog lines are typed too.** `gz-ui`'s logged answers of `-nodlg` and MCP (`~ [dlg suppressed] ...`, `* [mcp] ... -> Yes`)
  were marks written into plain log lines; they are warning / information findings now (`[dlg suppressed] X  -> auto-answer: No`,
  `[mcp] X -> Yes`). That is outside the six files the brief named, but "nothing writes a mark" needs it.
- The log FILE keeps its marks: `tools/qa` and people read them. Only `gz-log`'s writer knows them.
- The compiler's `! ERROR: ...` warnings become problems of severity Warning with the text `ERROR: ...` (the mark goes, the word
  stays: it is the compiler's own text).
- `bake_note`'s `WARNING:` line prefix (`gz-export-level` `cmd.rs`, read by `gz-ui-mod` `add_bake_note`) is a mark in a text
  too. I left it: it is a note string, not a log line, and the brief names the places. It wants the same treatment (a list of
  findings in the answer).
- **What the check cannot see.** A citation of an old function by a bare name (`(`Commit`)`) cannot be recognised without
  knowing the old program's symbol table. The sweep removed the ones the scanners found (backticked PascalCase names that are no
  item of this workspace; 1500+ of them); the families above are what the check enforces. 43 lines that my scanner still flags
  are real names of other programs' interfaces (Win32 calls in `gz-win`, the LZHUF routine names in `gz-chunk`, the game's
  `LVL_CHNG`, `NO_RANK`, `EngineAbilities`) and stay.
- **The game's own names stay and need no allow-list entry**: the server entity classes (`CSE_ALifeObject`, `STATE_Read`,
  `UPDATE_Write`) in `gz-entities`, the `.ogf` chunk ids (`OGF_S_MOTIONS`), the engine's `.level` file keys. They are the format.
- Where an algorithm is a port of X-Ray's own compiler / exporter and its result has to match (`gz-lc`, `gz-lc-light`,
  `gz-fmt-ogf`), comments say "the original compiler / exporter" where the match is the why. That is a fact about the
  algorithm's origin, not a history of this repository (about seventy files).
- Tests deleted: `gz-export-level/tests/golden.rs` and its `tests/data` (three tests: the level exports against the old
  editor's bytes), `gz-lc-light` `the_jitter_tables_are_the_cpp_ones` (a table's constants), `gz-ui` `names_are_the_cpp_tables`
  (constants), `gz-ui-app` `marks_and_trace_frames` (a reader that is gone; its second test now asserts the level is the
  record's and the text untouched). Twelve tests whose names said "the C++" assert real behaviour and were renamed
  (`the_spawn_layer_is_written_in_its_fixed_form`, `checks_with_the_documented_codes`, ...). I did not go through every test for
  duplicates; the aim was the parity ones.
- The editor's three files of the architect (`gz-win/src/lib.rs`, `gz-app/src/stalls.rs`, `gz-app/src/window.rs`) needed no change:
  no hit of the check, and a `::ui_tab` path is no mention. I did not touch them.
