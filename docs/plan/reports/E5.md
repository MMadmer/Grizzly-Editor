# E5 - what no command could bring into view, and the kit's proofs

Closes the `minor` findings of the critic's second round (section 5) named in `docs/plan/briefs/E5-popups-kitsheet.md`.
Pictures are in `Intermediate/plan/e5/` (all looked at).

## What was built

1. **A count that is not known yet is no count** (`gz-ui-level/place.rs`, `gz-ui/section.rs`). `Row::Header.count` is
   `Option<usize>`: `None` while the category's list is read. The kit's `Section` gained `busy(what)`: the spinner
   stands after the title where the count would, the count is dropped, and an audited frame reports `what` as
   `loading` whether the fold is open or not. `level.view`'s categories answer `count: null, loading: true`. Unit test
   `a_list_being_read_has_no_count`. (The kit file `section.rs` is the one kit file touched besides the sheet; it is the
   same widget the brief names, and the sheet shows it.)
2. **`loading` has a control.** Kit test `an_audited_frame_reports_every_busy_mark_and_only_those` (`gz-ui/tests.rs`):
   `busy_line`, `card_busy`, `Section::busy` and a dialog's `Footer::busy` give one `Loading` entry each, nothing
   without them, nothing when no audit was asked for. Suite check: `test_ui_shell` phase **K** (the last phase: it
   ends the suite's editor and starts a fresh one on the copy with `ready="ping"`, and looks at every frame from the
   first answer): `ui.audit` answers a non-empty `loading` while the editor reads the project it opens (seen on every
   run: `Place###LeftBar` "Reading the list...", the new header busy mark, 5 entries), and an empty one once it is read.
   A project that is already open cannot be made to wait on purpose (nothing the suite controls holds a surface busy), so
   the one deterministic busy window is the start.
3. **The popups a command can bring into view.** `world.view show=add_level|add_area_level` (the two Add Level lists of
   More: unfolds More and the section, switches the list on, refused without a linked game) and
   `mod.view show=add_requires|add_load_after|add_load_before|add_conflicts|function` (the four Add Module lists, and the
   Function list of the first command; refused, saying why, when the module has no command). The shape is
   `characters.view show=`: a request by name (`gz_ui::menu::show_popup`) that the page answers on its next frame
   (`take_popup_request`); a request is not spent on a button that is off. Wrong values are refused with the real ones.
   `ui.contract`'s `popups` names them (`<command> show=<value>`, 15 new entries including `characters.view`'s eight).
   Suites: `test_world` (U) and `test_build_contents` (U) open every list, check the rows, take a picture, close with
   `ui.popup show=none`, check it is gone. **Found and fixed on the way:** the Function list of Mod Settings was drawn
   only for the FIRST command row (`pick_at` kept the first row's anchor), so the chevron of any other row opened a list
   that was never drawn.
4. **No frame makes a thread.** `gz_ui::file_dialog::pick` takes `&Executors` first and starts its thread with
   `Executors::thread`. `gz-ui` now depends on `gz-task`. The old signature is gone (there was no caller in
   `gz-ui-previews`; every caller had `editor.exec`): `gz-ui-app/folder.rs` (2), `gz-ui-level` (`detail_objects`, `level_cmds`,
   `motion_ui`, `tools`), `gz-ui-mod/call.rs`, `gz-ui-pda/screens/doc.rs`, `gz-ui-release/submit.rs`. The kit's tests use a
   `Runtime`.
5. **The kit sheet** (`-kitsheet`) now shows: keycaps; form fields (`hint_field` empty and typed, `row_field` empty and
   typed, `secret_field` empty and typed); the empty `PickList` ("Nothing to pick"); `Section::busy`; the empty `ItemRows`;
   the `PropertyGrid` (required, modified with Reset, invalid with its message, read-only, mixed); `table_headers` and
   `table_headers_ruled`; `nav_row` (count, dot, dim, selected, action); a `banner` in Info; `busy_line`; `card` (with the
   attention strip) and `card_busy`; toasts (four buttons queue one of each tone); dialogs (a plain one with a status and
   a busy one with `Footer::busy` and its Stop); `error_state`. Compared with the table of section 4 row by row; **not on
   the sheet:** `page`, `page_card` + `card_footer` (they fill the work area), `confirm` / `unsaved_prompt` / `notice` /
   `result` (a person's questions, shown by the dialogs of the surfaces), `splitter*`, `drop` (lights up under a drag),
   `text::fit`, `upload::Tiled`, `audit`, `file_dialog` (no picture), the Combo's "open" state (the sheet's inline
   PickList is what it opens), "No matches" of the PickList (needs a typed query; the sample shows "Nothing to pick").
6. **Crate docs.** `gz-ui-content/lib.rs` (`local_checker` is the kit's `gz_ui::checker`) and `gz-ui-level/lib.rs`
   (`local_tab` is the kit's tabs). Every other surface crate's `lib.rs` read against its `local.rs`: they match
   (`gz-ui-previews` is E4's).

## Not proven

- `ui.list` does not name a kit pick popup (only menus, the tab menus and the Task card are noted there), so the brief's
  "`ui.list` shows the popup" is `ui.audit`'s rows plus the picture. `ui.popup` refuses the new `popups` entries (they
  are put up by their view command): the contract line says so, but `chrome.rs`'s `unknown popup` message could point at
  them (not my file).
- `show=function` without a command is refused by the code; the suites' project has commands, so the refusal text is
  only exercised when a project has none (the check is written for it and was not run in that state).
- Phase K proves `loading` at the project's start only; the dialog footer's busy mark and a card's busy line are proven by
  the kit test, not by a suite. The Place header's "no count" is proven by the unit test and by the header's busy mark
  seen in `ui.audit`; the suite did not catch the moment a `level.view` answer carried `loading: true`.
- The kit sheet's dialogs and toasts need a click; the pictures show the buttons, not the dialog open.
